  • ① 구조적 안전망(전 페이지): (user)/error.tsx · (auth)/error.tsx route-level 경계 신설. 서버 컴포넌트 fetch throw + 미포착 클라이언트 throw를 모든 페이지에서 헤더 유지한 "다시 시도" UI로 흡수(기존 Sentry+webhook 로깅 계승). → blog·library·guidebook·vod 상세(서버 컴포넌트)는 이 경계로 커버.

  • 미조치(의도적): challenge/*/latest 리다이렉트 9개·live/.../notification는 자체 error→redirect로 이미 안전. useProgramQuery류 공유 plain 훅은 전환 시 타 페이지 파손 위험이라 래핑만.
핵심 진단 — 전역 안전망이 사실상 없음
  • 세그먼트 error.tsx 0개. 라우트 어디에도 세그먼트 단위 에러 경계가 없어, 던져진 에러는 상위로 계속 전파되어 루트 global-error.tsx까지 올라가 페이지 전체를 통째로 교체합니다.
  • 루트 layout.tsx에 ErrorBoundary·Suspense 없음. 전역 폴백이 없습니다.
  • QueryClient retry:0 + 전역 throwOnError 미설정 (context/Providers.tsx). 일반 useQuery 에러는 error 상태로만 잡히지만, useSuspenseQuery·throwOnError:true는 즉시 에러를 던집니다. 상위에 경계가 없으면 100% 크래시.
  • 따라서 위험의 본질은 “한 파일에 모든 로직이 몰려 있고 그 파일이 페칭도 하는데 경계가 없음” → 그 한 파일의 에러가 페이지 전부를 무너뜨림.

💥 크래시가 발생하는 3가지 경로

① 경계 없는 useSuspenseQuery

Suspense는 있어도 ErrorBoundary가 없으면(=AsyncBoundary가 아니면) 쿼리 실패가 그대로 튀어 페이지 붕괴. report/management가 대표 사례.

② throwOnError:true + 경계 없음

의도적으로 에러를 던지지만 상위 AsyncBoundary가 없으면 크래시. 현행 challenge 대시보드는 올바르게 감쌌지만, 다수 페이지는 경계 없이 다수 useQuery를 나열.

③ 서버 컴포넌트 async fetch / undefined 역참조

Server Component의 await fetch나 Promise.all이 throw하면 세그먼트 붕괴. 렌더 중 undefined 데이터 접근도 동일. blog·library 상세, home이 해당.

📋 전체 페이지 감사 표

행을 위험도/도메인별로 필터링할 수 있습니다. 라인 수(파란색)가 클수록 “한 파일 집중”이 심해 붕괴 반경이 큽니다.
